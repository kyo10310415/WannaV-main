# WannaV Dashboard

認証機能を備えた複数システムへのリンク管理ダッシュボード

## 🎯 概要

WannaV関連システムへのアクセスを一元管理するダッシュボードです。ログイン認証により、許可されたユーザーのみが各システムにアクセスできます。

## ✨ 機能

### 認証機能
- ✅ ログイン/ログアウト機能
- ✅ セッション管理（7日間有効）
- ✅ Cookie-based認証
- ✅ 未ログイン時の自動リダイレクト
- ✅ **SSO（シングルサインオン）対応** - 1回のログインで全外部システムにアクセス可能

### ユーザー権限管理
- ✅ **3段階ロール制御**（管理者・リーダー・クルー）
- ✅ ユーザーの追加・削除（管理者、またはcrewのみ管理可能なリーダー）
- ✅ パスワード変更機能
- ✅ 管理者・リーダー権限の付与
- ✅ **初回ログイン時の強制パスワード変更**（admin以外）
- ✅ 新規ユーザーの初期パスワードは「1111」

### システムリンク管理（リーダー以上）
- ✅ リンクの追加・編集・削除
- ✅ **リンク単位の権限設定**（管理者・リーダー・クルー）
- ✅ 表示順序の管理
- ✅ 説明文の設定
- ✅ **権限に応じたリンクの自動フィルタリング**
- ✅ **トークンベース認証でSSO実装** - 外部システムを自動的に保護

## 🚀 デプロイ方法

### Renderへのデプロイ

1. **GitHubリポジトリと連携**
   - Render.comにログイン
   - 「New Web Service」を選択
   - このリポジトリ（WannaV-main）を選択

2. **環境設定**
   ```
   Name: wannav-dashboard (任意)
   Environment: Node
   Build Command: npm install
   Start Command: npm start
   ```

3. **環境変数の設定**
   ```
   JWT_SECRET=your-random-secret-key-here
   NODE_ENV=production
   ```

4. **デプロイ**
   - 「Create Web Service」をクリック
   - 自動的にビルド・デプロイが開始されます

### ローカル開発環境

```bash
# 依存関係のインストール
npm install

# データベース初期化
npm run init-db

# サーバー起動
npm start

# または開発モード（ホットリロード）
npm run dev
```

サーバーが起動したら http://localhost:3000 にアクセス

## 📊 データベーススキーマ

### users テーブル
- `id`: ユーザーID
- `username`: ユーザー名（一意）
- `password`: ハッシュ化されたパスワード
- `role`: ユーザー権限（'admin', 'leader', 'crew'）
- `must_change_password`: 初回ログイン時のパスワード変更フラグ
- `created_at`: 作成日時

### systems テーブル
- `id`: システムID
- `name`: システム名
- `url`: URL
- `description`: 説明文
- `required_role`: 必要な権限レベル（'admin', 'leader', 'crew'）
- `order_index`: 表示順序
- `created_at`: 作成日時

### sessions テーブル
- `id`: セッションID
- `user_id`: ユーザーID
- `token`: JWTトークン
- `expires_at`: 有効期限
- `created_at`: 作成日時

## 📝 使い方

### 一般ユーザー（クルー）
1. ログインページでユーザー名とパスワードを入力
2. 初回ログイン時はパスワード変更が必要
3. ダッシュボードから自分の権限でアクセス可能なシステムを表示
4. 各リンクをクリック → **SSO認証で自動的に外部システムにログイン**

### リーダー
1. クルーの全機能に加え、「管理」ボタンにアクセス可能
2. ユーザー管理：ユーザーの追加・削除・パスワード変更
3. システムリンク管理：リンクの追加・編集・削除・権限設定

### 管理者（admin）
1. リーダーの全機能に加え、管理者権限の付与が可能
2. すべてのシステムリンクにアクセス可能
3. ユーザーに管理者・リーダー権限を付与可能

## 🔐 SSO（シングルサインオン）機能

### 仕組み
1. ダッシュボードでログイン
2. 外部システムリンクをクリック
3. **自動的にトークンが生成され、外部システムに認証情報を送信**
4. 外部システムがトークンを検証
5. 認証成功 → 外部システムにログイン完了（再ログイン不要）

### 外部システムの保護
- すべての外部システムが自動的に認証で保護されます
- トークンなしでの直接アクセスは自動的にダッシュボードにリダイレクト
- トークンの有効期限は5分（Cookieは7日間保持）

### SSO統合ガイド
外部システムへのSSO統合方法は `SSO-INTEGRATION-GUIDE.md` を参照してください。

## SEC-009 / SEC-010：配備前の確認

`JWT_SECRET`は32文字以上の十分にランダムな既存共有鍵を必須とします。未設定・短い値・公開された既定値では、DB初期化とHTTP開始より前に起動を拒否します。値をログやコードへ書かないでください。現在の共有鍵が有効なら、コード配備だけで鍵は変更されずSSOのトークン形式も維持します。

過去に既定値を使用していた場合は、WannaV-mainだけで鍵を交換せず、全SSO連携先と調整してローテーションし、既存セッションも失効させてください。本変更は認証情報・本番設定・本番セッションを変更しません。

| 操作 | admin | leader | crew |
|---|---|---|---|
| crewの作成・パスワード変更・削除 | 許可 | 許可 | 拒否 |
| admin/leaderの作成・パスワード変更・削除 | 許可 | 拒否 | 拒否 |
| 権限の変更 | 既存の管理者専用ルート | 拒否 | 拒否 |

既定管理者の削除禁止は維持します。管理画面の作成候補とパスワード・削除ボタンにも同じ制限を適用します。leaderによる同権限leaderの作成・変更もできなくなるため、必要な操作はadminへ依頼してください。パスワード変更・削除では既存どおり対象セッションを失効させます。

`npm test`は外部API・実DB・HTTP待受けを使わない権限テストです。DBとbcryptをmock化した本番用ハンドラーを検証します。新規依存・DBschema変更はありません。既存の共通初期パスワード方式、SSO発行先の権限検査（SEC-011）などは今回の対象外で、追加対策が必要です。

### SSO宛先・権限検証（SEC-011）
SSO発行APIは登録済みsystemのrequired_roleを検査し、未登録URL・不正ロール・権限不足を拒否します。既存のtargetUrl完全一致指定を維持し、数値systemId指定にも対応します。登録URLはHTTPSかつ資格情報・query・fragmentを含めないでください。JWTはHS256、issuer=https://wannav-main.onrender.com、audience=登録URLのoriginを付与します。受信側もissuer/audience/roleを検証する必要があります。特典システムの受信側修正と設定は別PRです。既存SSO Cookieは受信側の切替時に再ログインが必要です。


### crewの担任Tutor対応付け（Notion同期）

担当者名は手入力せず、Notionの「メールアドレス」と共通ダッシュボードのusernameを完全一致で照合し、「Notion名」を取得します（大小文字の変換・別名/部分一致の推測はしません）。メール一致行と、そのNotion名を使う担当者行が両方一意であることを確認します。重複・空欄・取得エラーでは権限を付けません。

RenderのWannaV-mainにNOTION_API_KEYを設定し、対象Notionデータベースをそのインテグレーションへ接続して読取り権限を与えてください。値をソース/ログ/チャットへ出さないでください。対象DBの既定IDは2f6c668b8d194ae3ba75f6acb5bb7ce2。変更時はNOTION_TUTOR_DATABASE_IDを設定します。複数データソースのDBはNOTION_TUTOR_DATA_SOURCE_IDも明示してください。API2025-09-03のdatabase→data source取得を使い、組込みfetchのみで新規依存はありません。

管理者が管理画面の「Notion接続を確認」で接続とプロパティ構成を確認し、対象crewの「初回承認・Notion同期」を1回実行します。leaderが任意のメール名でcrewを作っただけでは担当権限を取得できないよう、管理者の承認を必須とします。起動時にnotion_tutor_approved列を加算し、既存・新規アカウントとも未承認(0)から始まります。管理者は「Notion連携を解除」もできます。

承認後はcrewが延長管理をダッシュボードから開くたびにNotionを読み直し、取得した名前だけをDBへ同期してtutorNameとして署名します。手動名やリクエストの偽装値、取得失敗時の前回名はSSO発行に使いません。他サービスのSSOやadmin/leaderの経路は維持します。管理画面の名は前回同期値の読取り専用表示です。Notion自体は変更しません。

メールはemail/rich_text/title、Notion名はpeople（ユーザー1人）/rich_text/title/select/文字列formulaを扱います。担当名は100文字以内の単一名で、制御文字・複数名区切り・前後空白を拒否します。必要な2プロパティだけを取得します。people型は表示名による検索ができないため、毎回最大10ページ（各100件）の担当表をメモリ内で確認し、別ユーザーを含む同名登録がないことを検査します。全件を確認できない場合は許可しません。複数人・空欄・取得省略されたプロフィールは拒否します。インテグレーションにはメールを含まないユーザー情報の読取り権限が必要です。曖昧な結果・429・timeoutは閉じて再操作を案内し、API応答原文は出力しません。接続診断は安全な結果コードとプロパティ名だけです。

取得済みSSOは最大1時間有効で、承認解除やNotion側変更による即時失効は未実装です。変更後はダッシュボードから開き直してください。受信側の担当生徒一覧は従来どおり、正常同期した最新集合/48時間期限とNotion担任Tutor名の一致で限定します。

Node22.23.4のnpm testで認可・不正SSO・Notion通信mock・重複メール/担当名・初回承認・解除・CSRF・偽装入力・schema/通信失敗・加算migrationを検証します。実Notionへの接続検証は個人データを取得しないschema診断のみとし、実アカウントの担当権限付与は管理者が行います。

同期エラー時は管理者画面の「照合のみ確認」でアカウント単位の原因を確認できます。この操作は担当対応・承認状態を変更せず、メール・担当名やNotion応答を返しません。登録なし、重複、プロフィール取得不可、利用回数制限を区別します。

peopleの一部ユーザー情報が省略される場合は、ユーザーIDから表示名のみを補完します（照合1回あたり最大20ID、永続化・ログ出力なし）。担当と異なる名前のBotなどがあるだけでは停止せず、同名があれば従来どおり拒否します。プロフィールを確認できない場合は許可しません。
